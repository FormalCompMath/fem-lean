# 审查与信任政策

[English version](../review.md)

## 信任模型

Lean 检查证明项是否具有所声明的类型；人类仍需检查该类型是否表达预期定理，以及
定义是否代表预期数学对象。因此审查优先级为：

1. 定义和表示方案；
2. 定理陈述及其假设；
3. 可编译示例和下游用途；
4. 证明的可维护性。

CI 全绿是必要条件，但其本身不等于数学语义审查。

## 定义审查清单

定义 PR 应给出标准数学定义、来源和 Lean 表示。审查者应检查：

- 显式与隐式参数、宇宙层级、coercion 和类型类搜索；
- 谓词、子类型、结构体或类型类是否为合适表示；
- 不变量和退化输入，例如空区域或退化单元；
- 边界、测度、范数和定向约定；
- 定义是否太弱而无法支持目标定理，或太强而排除预期应用；
- 有用时，是否证明与标准表述等价；
- 是否有具体例子能够暴露意外或空泛的定义。

核心表示修改应关联 RFC，并用小型下游示例比较候选方案。

## 定理陈述审查清单

审查证明之前，先比较自然语言陈述和 Lean 类型：

- 量词顺序和隐式变量；
- 连续性、强制性、对称性、正则性和边界假设；
- 对固定网格还是整个网格族进行量化；
- 范数和半范数的选择；
- 不等式方向以及强制性和连续性常数；
- 常数对维数、多项式次数、区域和形状正则性的依赖；
- 形式化版本相对来源是否更强、更弱或有所不同；
- 非空泛性以及至少一个预期的具体实例。

与来源的任何差异都必须写入 PR 和蓝图。已经批准的陈述如果发生变化，原有语义
批准即失效，需要重新审查。

## 用示例测试接口

示例是经过编译的数学检查，不是装饰性文字。早期有用的示例包括：

- 节点基函数在节点处满足 Kronecker-delta 性质；
- 仿射参考映射将参考顶点映到正确顶点；
- 离散空间等于连续空间时恢复弱解；
- 模型双线性形式满足抽象变分接口；
- 能从新的一般定理推出一个熟悉的推论。

示例位于下游，库模块不能导入它们。

## 证明审查清单

陈述固定且 CI 成功后，正确性由内核保证。人类证明审查主要关注：

- 是否出现值得提取为引理的重复论证；
- 是否意外依赖具体模型；
- 实例、coercion、记法或自动化是否不稳定；
- 是否可以复用 Mathlib；
- 证明脚本是否脆弱，是否存在不必要的 heartbeat 提升；
- 文档和模块位置是否合适。

## 持续信任检查

`main` 不能包含证明占位符或项目自定义公理。CI 使用 `axiom-audit` 审计
`FemLean` 根命名空间，只允许：

- `propext`；
- `Classical.choice`；
- `Quot.sound`。

该检查覆盖占位符公理、`native_decide` 信任扩展和自定义公理，包括传递依赖。
里程碑发布在条件允许时还应公开主要声明的 `#print axioms` 输出。

蓝图声明检查只能保证引用的 Lean 名称存在，不能证明自然语言和形式化陈述一致；
后者始终需要人类审查。

## 批准规则

- 作者不能是自己的唯一审查者；
- 普通结果至少需要一个独立批准；
- 核心接口和共享表示的破坏性修改通常需要 RFC 和两个批准；
- 后续提交会使旧批准失效；
- 合并前必须解决全部审查讨论。
